> 整合自 `docs/work-log/`、git `fix:` 提交和评测证据，每条按"问题 → 排查 → 解决 → 一句话回答"组织，供面试问答使用。
> 原则：只收录真实发生过、有 commit/评测记录佐证的问题，不虚构。

## 一、错误分类与异常处理

### 1. 异常继承顺序吞掉了 HTTP 错误

- **问题**：HTTP 层失败分类改造后，评测里始终看不到 `http_error` 类别。
- **排查**：发现 `_load_sync()` 中 `except URLError` 写在 `except HTTPError` 之前，而 `HTTPError` 是 `URLError` 的**子类**——所有 404/500 都被通用的 URLError 块先吞掉了。
- **解决**：调整 except 顺序，把子类异常放在前面（commit 见 `2026-06-23-http-error-classification.md`），并为三种错误类型（`PageTimeoutError` / `PageHttpError` / `PageEmptyError`）各写一个触发测试。
- **一句话**："我做失败分类时踩了一个经典坑：except 顺序没按异常继承层级排列，子类异常永远匹配不到。之后每个错误类别都有对应的触发测试，而不是只测 happy path。"

### 2. "browser_error" 是一个无用的失败类别

- **问题**：早期评测里所有 URL 失败都归为 `browser_error`，无法指导处理策略。
- **解决**：细分为 `http_timeout`（要重试）、`http_error`（标记 URL 过期）、`empty_page`（JS 渲染，切视觉抽取）、`browser_error`（兜底）。分类依据是异常类型而非字符串匹配。
- **一句话**："失败分类的价值在于驱动不同的恢复策略——超时要重试，404 要换 URL，空正文要转视觉抽取。我的 Agent 恢复链就是建立在这套分类上的。"

## 二、资源生命周期

### 3. Windows 下 SQLite 文件被锁（WinError 32）

- **问题**：HITL benchmark 在 pytest 清理临时目录时报 `PermissionError: [WinError 32]`，看起来像 checkpoint 场景失败。
- **排查**：根因与审批逻辑无关——Python 的 `with sqlite3.Connection` 只管理事务提交/回滚，**不会关闭连接**；Windows 因此仍锁定数据库文件，临时目录删不掉。
- **解决**：给 `JobRepository` 增加显式关闭连接的 context manager，成功和异常路径都执行 `close()`，并加"运行后可删除数据库文件"的回归测试。修复独立成 commit `ec0d033`，不混入幂等功能提交。
- **一句话**："这个 bug 教会我两件事：一是 `with conn` 在 SQLite 里不等于资源释放，Windows 文件锁会把它放大成清理失败；二是平台相关的修复要单独提交，保持每个 commit 意图单一。"

### 4. Playwright 浏览器资源泄漏与幂等关闭

- **问题**：真实 Qwen-VL provider 跑完后出现 `unclosed transport` 警告；comparison 路径评测失败时浏览器直接泄漏。
- **解决**：三层修复——① `close()` 调用链贯穿 `VisualJobExtractor → QwenVisualExtractorAdapter → CLI finally 块`；② `PlaywrightBrowserClient.close()` 幂等化（未启动、重复关闭都安全）；③ comparison 的 provider 评测包在 `try/finally` 里保证异常路径也释放。
- **一句话**："浏览器是重资源，我把它做成了从组件到 CLI finally 块的完整 close 链，并把 close() 设计成幂等的——资源清理代码恰恰是最容易被调用两次或一次都不调的代码。"

## 二点五、跨服务边界（双仓库桥接）

### 5. 双重获取：provider 自带浏览器导致的重复请求

- **问题**：视觉 provider 模式下，workflow browser 先 `open_url()` 抓一次文本（浪费），provider 又用自带 Playwright 截图抓一次——同一 URL 两次 HTTP 请求。
- **解决**：用 `uses_own_browser` 能力信号做协商——demo extractor 声明 `False`（依赖 workflow 提供页面），真实 provider 声明 `True`；`_browser_node` 检测到 True 就跳过自己的抓取，只创建占位 `BrowserPage`。
- **一句话**："这是一个职责边界问题：谁负责获取页面，必须由能力声明决定，而不是让两层默默各抓一次。测试验证了 browser 确实没有被调用。"

## 三、质量门与退出码语义

### 6. VLM 调用成功 ≠ 抽取有效

- **问题**：Qwen-VL 调用返回 200，但字段全是 `Unknown Title` / 空正文 / 零置信度——这些被计入 `visual_extraction.successes`，看起来抽取成功了。
- **解决**：加质量门 `_visual_fields_are_meaningful()`：title、company、body、confidence 任一为占位值就返回 `success=False`，触发文本抽取回退，并计为 failures。连"只有 title 没有 body"的 title-only 结果也拒绝。
- **一句话**："外部 API 成功和业务成功是两回事。我在 adapter 层加了质量门，把'模型响应了但没抽出东西'显式变成失败，让回退链能被触发。"

### 7. 空结果静默 exit 0

- **问题**：provider smoke 跑出 `Valid jobs: 0` 但退出码是 0——CI 和脚本会认为验证通过。
- **解决**：smoke 路径 `valid_jobs == 0` → exit code 2 + 打印抽取统计（attempts/successes/failures）、verifier 过滤原因和排查建议；comparison 路径**保持** exit 0，因为横向对比的职责是测量，不应因单行失败而中断。
- **一句话**："退出码是给自动化看的 API。我区分了 smoke（空结果就是失败）和 comparison（失败是一行数据）两种语义，而不是一个全局 exit code 走到底。"

## 四、Agent 决策安全

### 8. LLM Planner 越权决策

- **问题**：接入 DeepSeek/Qwen planner 后，LLM 可能输出不在当前状态下授权的动作（打开候选列表外的 URL、自行 FINISH、重复抽取）。
- **解决**：`_planner_decision_is_authorized()` 白名单校验——目标 URL 必须在候选列表且重试未超限；LLM 无权 FINISH；抽取动作的目标必须等于当前页。非法决策全部降级为确定性 fallback。真实 benchmark 佐证：DeepSeek 15 次调用中 5 次被 runtime 拒绝并安全 fallback，终止率仍 5/5。
- **一句话**："我不信任 LLM 的输出，只把它当建议。授权校验是代码不是 prompt——真实运行中 DeepSeek 有 5 次越权全部被拒，这证明安全边界在代码层真实生效。"

### 9. Agent 提前宣告完成

- **问题**：policy 在达到目标数量后直接 FINISH，跳过了匹配和保存——用户拿到了岗位却没有任何持久化结果。
- **解决**：完成顺序强制为 匹配 → 保存 → 才允许以 `target_reached` 终止（commit `85791d8`）。
- **一句话**："终止条件不只是'目标达成'，而是'目标达成且收尾动作完成'。策略层把业务完整性编码进了状态机。"

### 10. 恢复打开的新页面没有被抽取

- **问题**：`open_page` 失败后成功恢复到新 URL，但 state 里的当前页指针没有跟上，后续抽取的还是旧上下文。
- **解决**：修复恢复路径的状态推进（commit `ff8f948`），保证 recovery 后的观察对象是真正打开的新页面。
- **一句话**："恢复逻辑最容易错的地方不是'重试'本身，而是重试成功后状态没有推进——我专门为'recovery 之后抽取的是新页面'补了回归测试。"

## 五、幂等与崩溃窗口

### 11. checkpoint 与业务库之间的崩溃窗口

- **问题**：HITL 恢复后如果"业务写入成功、checkpoint 尚未提交"时进程崩溃，replay 会产生第二次可见副作用。
- **解决**：`approval_id` 作为业务 SQLite 事务里的唯一 receipt 键，岗位写入和 receipt 写入在同一事务——重复恢复被 receipt 拦截。评测证据：replay 重复副作用为 0。
- **一句话**："checkpoint 解决'从哪继续'，业务 receipt 解决'是否已经发生过'，两个职责缺一不可。我让审批 ID 成为两者之间的连接键，形成 exactly-once 的可见保存。"

### 12. 规则抽取在真实页面上全军覆没（诊断故事）

- **问题**：8 个真实招聘页上规则抽取只完成 2/8；匹配分数全为 0。
- **排查**：Greenhouse 真实页面没有 `Title:` / `Requirements:` 这类标签行，规则解析直接失效；抽出的"技能"字段是整段需求文本而非关键词列表，精确匹配自然全 0。
- **解决**：低置信度页面自动升级 LLM 抽取（DeepSeek/Qwen 达到 7/8）；匹配层引入语义匹配 fallback（4/7 岗位发现 `LangGraph`↔"Agentic AI" 这类关联）。
- **一句话**："这个失败让我建立了项目的核心分层：规则优先（免费、可测）、LLM 兜底（贵、准）、失败分类记录（诚实）。每次升级都由置信度触发，而不是无条件调用模型。"

## 六、配置与环境（2026-08-31 中文管线阶段 0）

### 13. 改了 .env 但 API 仍然 401：OS 环境变量覆盖链

- **问题**：DASHSCOPE key 失效后在 `.env` 里更新，但 CLI 跑 LLM 抽取仍然 401 `invalid_api_key`；直接解析 `.env` 手动调 API 却是 200。
- **排查**：对比两条路径读到的 key——`load_dotenv()` 读出的值与 Windows 用户环境变量里的旧 key 相同（41 字符），而 `.env` 文件里是新 key（36 字符）。`load_dotenv()` 默认 `override=False`：**已存在的 OS 环境变量优先于 .env 文件**。旧 key 残留在 Windows 用户环境变量里，把 `.env` 的更新完全屏蔽了。
- **解决**：运行时显式内联 `DASHSCOPE_API_KEY=<.env 值>` 强制覆盖。
- **一句话**："排配置问题要沿读取链逐层对比实际值，而不是假设最后一层生效。python-dotenv 默认不覆盖已有环境变量——'改了 .env 不生效'时这是第一嫌疑。"

### 14. 用 /models 端点验证 API key 得到假阳性

- **问题**：验证 DASHSCOPE key 时用 `/v1/models` 列表端点返回 200，判定"key 有效"；随后真实抽取调用全部 401。
- **排查**：用垃圾 key 请求 `/v1/models` 同样返回 200——该端点不校验鉴权；`/chat/completions` 才做真实校验。
- **解决**：验证 key 一律用将要实际调用的端点发一次最小请求（`max_tokens=5` 的对话）。
- **一句话**："健康检查端点和业务端点的鉴权强度可能不同——验证凭证要打在真实使用的端点上，否则拿到的是假阳性。"

### 15. 中文 JD 被英文关键词过滤器全量误杀

- **问题**：LLM 抽取在 6 个牛客中文 JD 上字段全部正确（confidence 1.00），但走完整 CLI 管线时 `valid_jobs: 0`——verifier 默认关键词 `["AI", "LLM", "Agent"]` 全小写后在纯中文正文里匹配不到，正确抽取的岗位被 `not relevant` 过滤。
- **排查**：对比评测报告的 failure counts（`verification_filtered=5`）与单组件冒烟结果（6/6 抽取成功），差异只出在 verifier 环节；读 `verifier.py` 确认默认关键词表无中文。
- **解决**：阶段 2 计划新增中文关键词（人工智能/大模型/算法/机器学习等）；冒烟脚本用 `required_keywords=[]` 诊断模式绕过，把抽取质量与相关性过滤两个问题解耦测量。
- **一句话**："全链路失败时先二分定位是哪一层——把过滤条件放空跑一次单组件冒烟，立刻区分'抽取不行'和'过滤误杀'。这个案例也说明：硬编码关键词的相关性过滤在多语言输入下天然脆弱。"

### 16. 中文 JD 的"标签行"和英文结构不同：section 式标签解析

- **问题**：给规则抽取加了中文标签和全角冒号支持后，牛客风格的中文 JD 依然抽不到 requirements/responsibilities——"任职要求："行被识别为标签，但值是空的。
- **排查**：对比真实页面版式发现结构性差异：英文 JD 是 "Requirements: xxx" 的**同行键值式**，中文 JD 的"岗位职责：/任职要求："是**值为空的 section 标题行**，内容在后续多行。只做"全角冒号替换"这类表面适配覆盖不了这个结构差异。
- **解决**：标签解析支持 section 式收集——标签行值为空时，逐行收集后续内容直到下一个标签行（`extractor.py` `_parse_labeled_lines`）。6 个真实牛客页 requirements/responsibilities 从 0/6 提升到 5/6。
- **一句话**："做解析器适配时，先看目标格式的真实版式再写代码——中文 JD 的'标签'其实是 section 标题，值不在冒号后面而在下面几行。表面字符替换解决不了结构差异。"

### 17. LLM 语义匹配的乐观偏差：无关岗位也被抬分

- **问题**：16 条人工标注的匹配评测里，LLM 语义匹配准确率 0.81 低于归一化后的规则匹配 0.94——LLM 在 3 个"明确不相关"样本上给了中高分数（测试开发岗 0.85、商业分析 0.65），只因为用户"会 Python"。
- **排查**：逐条对比分歧样本——LLM 的失败全部集中在"方向不匹配但技能词有交集"的样本；规则失败在"语义等价但词面无交集"的样本（各 1 条，#5 只有 LLM 判对）。
- **解决**：维持分层设计——规则优先做硬过滤（快、稳、免费），LLM 只在规则低分时兜底语义边界；分歧数据记录为未来混合仲裁策略的输入，本轮不做。
- **一句话**："评测让我发现 LLM 匹配器的系统性偏差：它对'不匹配'过于乐观。规则和 LLM 各自在对方失败的象限里更强——这不是谁替换谁的问题，是分层依据。"

### 18. 技能缩写裸子串匹配：简历写 HTML 被记为会机器学习（2026-08-31 bug 排查）

- **问题**：阶段 3 别名归一化上线后，写了个"纯前端简历"（HTML/CSS/YAML/XML）做对抗测试——机器学习岗位匹配分 1.0，`matched_skills=["机器学习"]`。
- **排查**：别名表为了中英互通收了缩写 `"ml"`（machine learning），简历扫描是裸子串 `term in text`——"html"、"yaml"、"xml" 全部含 "ml" 子串。同理 "dl"（deep learning）会命中 "handlebars"，"tf" 会命中任何含 tf 的词。中文技能词没有这个问题（CJK 词不会互为子串），纯属 ASCII 缩写特有。
- **解决**：`skill_variants` 扫描改为 `term_in_text()`：纯 ASCII 词用字母数字 lookaround 边界 `(?<![0-9a-zA-Z])ml(?![0-9a-zA-Z])`（不用 `\b` 是因为 Python re 里 CJK 也算 word char，"熟悉ML"会丢命中），含 CJK 词保持子串。加了"前端简历不得被记为会机器学习"回归测试。
- **一句话**："给中英混排文本做缩写子串匹配，一定要加 ASCII 边界——HTML/YAML/XML 都含 'ml'。而 `\b` 在 CJK 相邻处不可用，需要 lookaround 自己定义边界。"

### 19. 官方 API 适配器自己拼的标签，抽取器认不出来（2026-08-31 bug 排查）

- **问题**：腾讯/美团官方 API 适配器拿到的 JD 字段完整（职责/要求都有），拼正文时用了复合标签头 `"岗位职责/任职要求："`——这个标签不在抽取器 `_LABELS` 里，规则抽取 requirements/responsibilities 全空、confidence 0.4，**每个官方 API 岗位都强制走 LLM 抽取**，白烧配额。
- **排查**：端到端结果一直"能用"，是因为 confidence 0.4 < 0.6 触发 LLM 兜底把字段补齐了——LLM 兜底**掩盖**了规则层失效。单独跑 `PageExtractor` 对官方 API 格式正文才发现规则层 0 命中。对照实验：同样的内容拆成 `"岗位职责：\n…\n任职要求：\n…"` 两个标准标签行，confidence 0.4→0.8。
- **解决**：适配器输出标准标签行（`公司：/工作地点：/岗位职责：/任职要求：`），规则抽取直接命中；加集成测试断言官方 API 正文 `confidence >= 0.6`（不依赖 LLM）。
- **一句话**："兜底层正常工作时，主路径坏了你是听不到响声的——测分层系统要逐层单独验收，别只看端到端。同一个系统里两处代码约定（适配器的输出格式 vs 解析器的标签表）没有共享常量，就是隐式耦合。"

### 21. 短内容页诱发 LLM 幻觉 JD：兜底数据要有信息量门槛（2026-08-31 合成简历 E2E）

- **问题**：合成简历端到端跑，腾讯青云计划岗的报告里出现了**完整的任职要求**（"硕士或博士在读""顶会论文优先"），置信度 1.00——但该岗位的正文来源是 49 字符的 jd_text 兜底，只有"标题+部门+城市"。
- **排查**：单独跑规则抽取该页：requirements 空、confidence 0.2——报告里的完整 JD 是 **LLM 从标题行幻觉编造的**。进一步统计 job-radar 全量 jd_text 长度：237 条实习+AI 岗中位数仅 46 字符、≥120 字符的只有 6 条——**jd_text 基本是标题行，不是 JD 摘要**，阶段 1"jd_text 兜底有信息量"的假设整个是错的。50 字符的有效内容门槛连第三方站 98 字符的浏览器兼容提示都放过了。
- **解决**：两层护栏——loader 层 `MIN_USEFUL_CONTENT_CHARS` 50→120 且 jd_text 兜底同门槛（无信息内容诚实进失败分类）；extractor 层正文 <100 字符禁止触发 LLM 抽取（防幻觉保险，不依赖 loader 挡住一切）。重跑后 12 URL → 7 页诚实失败、5 个有效岗位全部真实内容，幻觉 JD 消失。
- **一句话**："兜底数据源必须先验证信息量分布再接入——中位数 46 字符的'摘要'其实是标题行，把它喂给 LLM 只会得到一本正经的编造。LLM 兜底和幻觉之间只隔着一个内容长度门槛。"

### 22. 规则匹配在真实中文 JD 上全 0：句子碎片与技能词永不相交（2026-08-31 合成简历 E2E）

- **问题**：三份差异化简历（CV 算法/Java 后端/数据分析）在真实美团 JD 上匹配分**全部 0.00**——CV 简历明写会 PyTorch、岗位明写要求 pytorch，依然 0 分。
- **排查**：看岗位侧 skills 的实际内容：`"1、扎实的算法基础, 熟悉NLP相关算法和模型；..."`——官方 API 的 requirements 是**编号长句**，规则 `_extract_skills` 按逗号切分，产出的是句子碎片而非技能词。句子碎片 ∩ 技能词 = 永远空集。此前带 LLM 的跑分（0.82/0.72）全靠 LLM 匹配兜底撑着，**规则层在真实数据上的失效被 LLM 兜底掩盖了**——和 #19 同一个模式。
- **解决**：skills 碎片化判定（>15 字符/含句读/编号开头）→ 降级为 **JD 文本技能词扫描**：词表+别名变体直接扫 requirements/responsibilities，按 canonical 去重后与用户信号求交集。干净 skills 走原精确交集路径，标注集评测 0.94 零回归。重跑后区分度正确：LLM 应用简历 0.72-0.82 > CV 算法 0.33-0.50 > Java 后端/数据分析 0.00。
- **一句话**："分层系统里每层都要单独在真实数据上验收——LLM 兜底正常的日子里，规则层坏了你听不见响声。中文 JD 的'requirements'是编号长句，逗号切分得到的不是技能是句子，匹配前先检查输入形态再选策略。"

### 23. 同一公司两套校招/社招库：API 逆向要从消费端 JS 找线索（2026-08-31 阶段 6A）

- **问题**：聚合源 91%（216/237）是腾讯岗，其中校招库（青云计划等 210 条）在 careers 社招库 ByPostId 接口全 E1005——占了绝对多数的岗位成为管线盲区，而社招岗同接口正常。
- **排查**：对比两类岗位的 source_id（cn-tencent vs cn-tencent-campus）发现腾讯有**两个独立的招聘门户**：careers.tencent.com（社招）和 join.qq.com（校招），postId 命名空间互通但详情接口不同。服务端 HTML 是 404 壳，不含路由信息。
- **解决**：从 join.qq.com 前端 JS bundle（751KB）的字符串里挖出完整 API 清单，找到 `GET /api/v1/jobDetails/getJobDetailsByPostId`（返回 topicDetail+topicRequirement 完整课题 JD）。careers E1005 → join.qq.com 详情两跳兜底，真实冒烟 3/3，规则抽取 conf 1.0 零 LLM 成本。
- **一句话**："API 逆向要从消费端 JS 找线索——服务端 HTML 是壳，真正定义接口清单的是前端 bundle 的字符串。同一公司的校招和社招往往是两套系统，不能假设一个 API 覆盖全公司。"

### 24. LLM 匹配的乐观偏差治理：规则低分时 LLM 分数折减，混合准确率追平规则（2026-08-31 阶段 6B）

- **问题**：#17 记录了 LLM 在"方向不匹配但技能词有交集"岗位上抬分（标注集 #8/#12/#14），当时的决定是"只记录不修"。真实跑分再次复现（商业分析岗对 LLM 应用简历 0.68），分歧数据已积累到可以定策略的程度。
- **排查**：候选策略三个（不折减/规则否决封顶/折半惩罚），用 16 条标注集跑数字对比。目标是 no_match 拒绝率与 match 召回的帕累托最优。
- **解决**：`llm_discount=0.55` 折减——规则低分（<0.6）说明关键词证据不足，LLM 兜底分数 ×0.55 后采用，reason 标注折减。混合准确率 0.875→0.94 追平纯规则，乐观错误 3 修 2（#8/#12），语义边界召回（#5）保留。折减的 reason 里写明系数，用户能看到分数为什么降。
- **一句话**："治理 LLM 乐观偏差不靠换模型靠仲裁信号——规则关键词命中不足就是现成的'不信任 LLM 分数'的信号，折减系数用标注集跑出来而不是拍脑袋。"

### 25. 缓存命中绕过内容门槛：修复只挡住了抓取路径（2026-09-01 阶段 6 重跑）

- **问题**：修完门槛（#21）重跑 E2E，valid 数没涨反而冒出 **5 个 duplicate**——12 个 URL 各不相同的岗位互判重复。
- **排查**：独立复现同一批 URL 抽取后 dedupe 为 0 重复，与 CLI 矛盾；查 page_cache 表发现门槛收紧（50→120）**之前**写入的旧缓存：腾讯 SPA 壳页 11 字符、第三方站兼容提示 98 字符，TTL 24h 内命中后直接绕过了新门槛。空壳页抽出相同 title → (company,title) 键互判重复。
- **解决**：常量统一到 browser.py，CachedPageLoader 与 AggregatorPageLoader 的缓存命中路径都过内容门槛，低于门槛视为缓存失效重新抓取并覆盖。实测重跑 valid 5→10。教训：**修 bug 时把同类数据的所有入口列全**——抓取路径修了，缓存路径漏了，因为"缓存里的数据是过去版本的代码写进去的"。
- **一句话**："内容校验要加在数据消费端而不是生产端——只要还有一条写入路径是老代码写的，或者 TTL 内还有旧数据，单点校验就形同虚设。"

### 26. 分数折减后派生字段没重算：0.40 分配 priority=high（2026-09-01 阶段 6 重跑）

- **问题**：折减上线后真实跑分出现"匹配分数 0.40 但优先级 high"的矛盾输出——LLM 自报 0.72/high，分数折减到 0.40，priority 却原样透传了 LLM 的 high。
- **排查**：priority 是分数的派生字段（_priority 阈值映射），但 LLM 兜底分支里 priority 直接取 LLM 返回值，没有跟随折减后的分数。
- **解决**：折减路径的 priority 改为按折减后分数重算，与规则层口径一致。
- **一句话**："改动一个权威字段时，检查所有从它派生的字段——分数打折了，由分数算出来的东西都要重算，否则报告自相矛盾。"

### 27. 修复不彻底的模式再现：official-api 路径与校招守卫仍是门槛漏洞（2026-09-01 bug 排查轮）

- **问题**：#25 修了"缓存命中过内容门槛"，但对抗审查发现抓取侧仍有洞：①官方 API 路径是**唯一不过 120 字符门槛的内容路径**——短正文既进管线（100~119 字符区间还恰好绕过 extractor 的 LLM 幻觉护栏）又被写缓存，缓存命中检查再拒收 → 该 URL 每次运行重调 API、缓存永不生效；②校招组装守卫 `len(labeled)<=1` 过弱，topicDetail/topicRequirement 全 null 时"公司+城市"约 15 字符的壳正文照样成功返回。
- **排查**：对抗审查 agent 用 37 字符的 stub 官方 API 实跑两次 loader：第二次缓存命中被 #25 门槛拒绝后重调 API、拿到同样短正文再次写缓存——缓存失效循环复现。
- **解决**：官方 API 分支与 http/jd_text 路径同一门槛（不足记 `official-api:too-short` 落兜底、不写缓存）；校招守卫改为要求至少一个 topic section 非空。
- **一句话**："修完'消费端校验'还要回查'所有生产端入口'——#25 教训的重演：这次漏的是官方 API 抓取路径。数据链路上任何一条没校验的写入路径都会让单点校验形同虚设。"

### 28. 通用错误码冒充业务错误码：Code:500 壳让瞬时故障伪装成岗位下线（2026-09-01 bug 排查轮）

- **问题**：E1005（岗位下线）判定用子串 `'"Code":500' in body`——但 Code:500 是腾讯 API 的**通用错误壳**，任意瞬时 500 都带它。瞬时故障会被误判为"岗位不可用"并触发 join.qq.com 校招第二跳（对社招 postId 是无意义的请求，还可能拿到误导性响应）。
- **排查**：HTTP 500 + `{"Code":500,"CodeDesc":"ServerError"}`（无 E1005）实测直接命中误判分支。
- **解决**：只认 `"E1005" in body` 业务错误码；通用 500 归类 PageHttpError（可重试语义）。瞬时错误和永久不可用必须区分——两者的正确处理动作完全不同（重试 vs 跳过）。
- **一句话**："错误分类要用业务语义字段而不是 HTTP 状态码的壳——同一个 500 可能是'岗位永久下线'也可能是'服务器打了个喷嚏'，混为一谈的代价是把重试逻辑接在永久失败上。"

### 29. LLM 采样抖动 × 阈值压线：评测指标是区间不是单值（2026-09-01 bug 排查轮）

- **问题**：修复后重跑标注集评测，混合准确率从 0.94 变 **0.88**——逐条对比发现 #12 的 LLM 分数从 0.65 抖到 0.75（同一 prompt 同一 provider），折减后 0.36↔0.41 恰好跨越 0.4 的 match 阈值，判定翻转。三跑数字：0.94 / 0.88 / 0.94。
- **排查**：排查顺序是先怀疑自己刚改的代码（max 下限/memoize/分母）——核对每条样本的计算路径确认修复零回归，抖动来自 provider 侧（temperature=0 也不保证逐字一致）。#12 恰好是"折减后压线"样本：LLM 分数 ±0.1 的抖动经 0.55 折减缩到 ±0.055，而它离阈值只有 0.04。
- **解决**：两份报告都版本化（`matcher-evaluation.md` + `variance-run1-0.88.md`），文档里混合口径标注为区间而非单值；不为指标好看去调阈值——压线样本的判定翻转不是能力变化，是采样噪声。
- **一句话**："对非确定性组件报指标要报区间——单值 0.94 和 0.88 都是真的，哪个出现在报告里取决于 provider 心情。修复自己的代码前先核对计算路径：压线样本的翻转最容易被误诊为新引入的回归。"

### 30. requirements.txt 中文注释 × Windows GBK locale：文件级编码假设在消费端爆掉（2026-09-08 云端部署验证轮）

- **问题**：为云端部署新写的 `requirements.txt` 带中文注释（符合仓库"文档用中文"的惯例），在 Windows 干净 venv 里 `pip install -r` 直接 `UnicodeDecodeError: 'gbk' codec can't decode byte 0xab`——pip 按系统 locale（cp936）读文件，而文件是 UTF-8。
- **排查**：报错栈指向 requirements 文件解析而不是某个包；Linux 云端（UTF-8 默认 locale）永远复现不了这个坑，恰好是本地仿真先替云端把问题拦了下来——如果直接推上 Streamlit Cloud，构建日志会更隐蔽。
- **解决**：requirements.txt 注释改 ASCII 并加注释说明"keep ASCII-only for locale-safe pip parsing"；仓库其他 UTF-8 文件（源码、文档）不受影响，因为 Python 3 源码默认 UTF-8、pytest 不走 locale 解码——只有"被外部工具按 locale 读的文件"需要 ASCII 兜底。
- **一句话**："编码假设要看消费端用什么解码——同一段中文注释，git/pytest/IDE 都当 UTF-8，pip 却按系统 locale 读。跨机器分发的配置文件要么纯 ASCII，要么带 BOM/显式编码声明。"

### 31. Streamlit Cloud Secrets ≠ 环境变量：凭据注入点要顺着"谁在消费"往上游找（2026-09-08 云端部署验证轮）

- **问题**：`build_configured_llm_*` 在构建时直接读 `os.environ` 取 API key，而 Streamlit Community Cloud 的 Secrets 只进 `st.secrets`、不自动注入 `os.environ`——如果只把校验层（`validate_ui_request`）改成读 secrets，会出现"校验通过、运行时 KeyError"的分层裂缝。
- **排查**：顺着 key 的消费链画图：校验层（可参数化）→ 构建层（`os.environ` 直读）→ HTTP 层（用构建层传的 api_key），发现注入点必须选在构建层之前，否则要改两层签名。
- **解决**：`sync_provider_secrets()` 在应用启动时把 secrets 一次性补进 `os.environ`（环境变量优先、不覆盖已配置值，本地无 secrets.toml 静默跳过），构建层零改动；配 5 项 TDD 测试覆盖"env 优先/secret 填补/无 secrets 文件不炸"。
- **一句话**："接平台适配层时先画出凭据/配置的完整消费链，注入点选在'直读全局状态'的那一层上游——只修看得见的校验层，裂缝会平移到运行时才爆。"

### 32. health 端点 303 三连误诊：探测手段本身要先做对照校准（2026-09-08 云端部署验证轮）

- **问题**：App 部署到 Streamlit Community Cloud 后，匿名 curl health 端点持续 303 到登录页——连续三轮按"配置未生效"处理（确认 Sharing 选项、re-toggle、Reboot），全部无效功。
- **排查**：换浏览器 UA、加缓存穿透参数、双网络出口交叉验证，303 纹丝不动；对照组实验一锤定音——**一个根本不存在的子域名** `xyzzy-nonexistent-*.streamlit.app` 返回一模一样的 303。这说明 303 是平台边缘对无浏览器会话流量的统一门禁，与 App 公开/私有状态完全无关，"health 匿名探测"这个验证手段本身失效了。
- **解决**：改用真实浏览器无痕窗口（无登录 cookie）做公开性验证——用户确认可直接打开，验证通过。探测手段校准的重要性高于对目标对象的任何操作。
- **一句话**："对黑盒平台连续三次'修配置'无效时，该怀疑的不是配置而是探测器——找一个'应该失败'的对照组（不存在的子域名），如果它和目标表现一致，说明信号源根本不携带你想读的信息。这是 A/B 思维在调试里的用法：先验证量具，再测量。"
