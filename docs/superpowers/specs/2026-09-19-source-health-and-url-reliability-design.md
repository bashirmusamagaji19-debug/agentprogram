# 来源健康度与岗位链接可靠性设计

## 背景

当前官方列表模式已经能从多个企业招聘 API 发现岗位，并通过“缓存 → 官方详情 API → HTTP → 列表 JD”逐级获得正文。2026-09-18 的真实体验修复了地点丢失、部分站点详情路由错误以及招聘门户上下文缺失，但仍有两个系统性缺口：

1. `OfficialListSource` 会把单个来源的任意异常静默转换为空列表。用户只能看到岗位变少，无法区分“该公司暂无岗位”和“适配器、网络或响应结构已经失效”。
2. `AggregatorPageLoader` 在详情 URL 返回永久失效信号后，仍可能使用列表自带 JD 生成岗位结果。内容可能真实，但用户看到的链接已经无法打开。

现有 `url_verification` 能描述正文证据来源，但 `list-attested` 只表示岗位来自当次列表响应，不代表详情链接已经独立验证。本设计保留这一区别，不把列表自证包装成详情页验证。

## 目标

- 对每个官方来源记录可解释的发现结果与失败原因，不再静默丢失来源。
- 区分岗位详情页的永久失效、访问受限、瞬时故障和空壳页面。
- 永久失效的详情链接不得通过列表 JD 兜底进入用户可点击结果。
- 访问受限或瞬时故障不得被误判为岗位下线；此时仍可使用列表 JD，但必须维持诚实的验证等级和诊断信息。
- 将来源级和页面级诊断写入运行状态、JSON 产物和 Streamlit“失败与诊断”页。
- 所有自动化测试使用注入式 fake/fixture，不依赖真实招聘网站。

## 非目标

- 本轮不建设定时调度、长期健康趋势或告警服务。
- 本轮不逐条启动真实浏览器验证 JavaScript 渲染结果。
- 本轮不保证外部岗位 URL 永久有效；系统只能报告当次运行得到的证据。
- 本轮不重构现有工作流、匹配算法或持久化结构。

## 方案比较

### 方案 A：仅记录来源异常

在 `OfficialListSource` 中保留每个适配器的成功数量和异常。改动最小，但不能阻止已失效链接进入结果，也无法满足真实点击可靠性目标。

### 方案 B：分层可靠性验证（采用）

同时增加来源诊断、页面失败分类和永久失效门禁。它复用现有加载链和 UI 诊断通路，能够解决已观察到的问题，同时避免引入调度与长期存储。

### 方案 C：持续巡检平台

周期性抓取所有来源并持久化历史、趋势和告警。覆盖最完整，但需要新的调度、数据模型和运维边界，不适合作为当前单轮改进。

## 架构

### 1. 失败分类模块

新增独立模块，提供无状态、可单测的分类函数。分类结果包含稳定的机器类别和面向人的简短说明。

页面失败分为：

- `removed`：HTTP 404/410，或成功响应中出现明确且受约束的岗位下线/页面不存在信号。
- `blocked`：HTTP 401/403/429 等访问控制或限流。它不证明岗位已下线。
- `transient`：超时、DNS、连接中断或 HTTP 5xx。它不证明岗位已下线。
- `empty_shell`：请求成功但正文低于现有有效内容门槛，常见于 JavaScript 空壳页。
- `unknown`：无法安全归入以上类别的异常。

内容中的下线信号只在标准化后的短页面、标题或明确状态字段中识别，避免岗位正文偶然提到“页面不存在”等词时产生误杀。分类模块不执行网络请求，也不直接决定工作流行为。

### 2. 来源级诊断

`OfficialListSource` 在每次 `discover()` 开始时重置本轮诊断，并为每个配置来源记录一条结果：

- 来源名称；
- 状态：`healthy`、`empty` 或 `failed`；
- 返回岗位数；
- 异常类型与脱敏后的简短错误说明（仅失败时）；
- 当前采样轮次或预算，便于解释补足轮行为。

单来源失败仍不终止其他来源，保持现有容错语义。相同来源在补足轮重复请求时，诊断合并为该来源的最终状态并保留尝试次数，避免 UI 出现多条难以理解的重复记录。

诊断数据只包含来源名、计数和异常摘要，不记录响应正文、简历、API key 或请求头。

### 3. 页面加载门禁

`AggregatorPageLoader` 继续使用现有顺序：缓存 → 官方详情 API → HTTP → 列表 JD。

行为调整如下：

- 官方详情 API 或 HTTP 返回 `removed` 时，立即终止该 URL 的加载并抛出带稳定类别的页面不可用错误，不再进入列表 JD 兜底。
- 返回 `blocked`、`transient`、`empty_shell` 或 `unknown` 时，记录分类后继续尝试下一层；若最终使用列表 JD，岗位保持 `list-attested`。
- 官方详情 API 返回可用正文及 canonical URL 时，继续沿用 `api-verified`。
- lister 已完成详情探测时，继续沿用 `detail-probed`。
- HTTP 获取有效正文时，继续沿用 `http-fetched`。

`resolution_log` 增加稳定的分类字段，但保留现有 `strategy` 文本，避免破坏已有调试与测试消费者。

### 4. 诊断透传

官方模式构建浏览器时，将 `OfficialListSource` 的本轮诊断与加载器一并保留。运行结束时，把来源诊断转换为现有诊断行结构：

```text
source_failed: <source> — <exception type>: <safe summary>
source_empty: <source> — no jobs returned
page_removed: <url> — HTTP 404
page_blocked: <url> — HTTP 403
```

页面永久失效会自然进入现有 `failed_url_errors`。来源诊断追加到 `UiRunResult.diagnostics`，并写入 `WorkflowState.metadata`，因此 JSON 产物与 Streamlit“失败与诊断”页使用同一份数据。

健康来源不作为失败行展示，但其结构化摘要保留在 JSON metadata 中，便于审计“哪些来源实际参与了本次运行”。

### 5. UI 语义

岗位表继续显示现有页面核验标签，不新增会让用户误以为已完成浏览器验证的标签。

诊断页按类别展示来源失败、来源空结果、页面永久失效、访问受限和瞬时故障。无诊断时的提示从“没有页面级失败”调整为“本次运行没有来源或页面诊断”，与扩展后的数据范围一致。

## 数据流

1. `OfficialListSource.discover()` 逐来源采集岗位，同时生成来源诊断。
2. 发现到的 URL 进入 `AggregatorPageLoader`。
3. 加载器对官方 API、HTTP 异常和页面内容做失败分类。
4. 永久失效 URL 进入 `failed_url_errors`；其他失败可继续降级。
5. 抽取器依据最终正文来源设置 `url_verification`。
6. runner 合并来源诊断、页面失败和 verifier 过滤原因。
7. JSON 产物与 Streamlit 使用相同的结构化诊断数据。

## 错误处理原则

- 只有强证据才能判定 `removed`。403、429、超时和 5xx 绝不等同于岗位下线。
- 单来源失败不影响其他来源，也不伪造空结果为健康。
- 诊断生成自身不得让主流程失败；无法分类时使用 `unknown`。
- 错误摘要必须限制长度，并避免包含响应正文、令牌、请求头和本地敏感路径。
- 对外展示稳定类别；具体异常类名和摘要只用于诊断详情。

## 测试设计

### 分类单元测试

- 404/410 → `removed`。
- 401/403/429 → `blocked`。
- 5xx、超时、DNS/连接错误 → `transient`。
- 明确短下线页 → `removed`。
- 正常长 JD 中出现相同词语不误判。
- 空壳正文 → `empty_shell`。

### 加载器测试

- HTTP 404 后不使用列表 JD，URL 进入失败诊断。
- HTTP 403、429、超时后允许列表 JD 兜底，验证等级仍为 `list-attested`。
- HTTP 有效正文仍为 `http-fetched`。
- 官方 API/canonical URL 和缓存行为不回归。
- `resolution_log` 同时保留策略与稳定类别。

### 来源测试

- 一个来源抛错、另一个来源成功时，成功岗位仍返回。
- 失败来源有 `failed` 诊断，异常摘要已截断且不含敏感正文。
- 正常空列表记录为 `empty`，与异常区分。
- 补足轮的多次尝试合并为单来源摘要。
- 连续两次 `discover()` 不复用上轮诊断。

### Runner 与 UI 测试

- 来源诊断写入 JSON metadata 和 `UiRunResult.diagnostics`。
- 页面永久失效、访问受限和 verifier 过滤原因均能渲染。
- 诊断为空时显示新的准确提示。
- Demo 与 seed URL 模式不产生虚假的官方来源诊断。

### 回归门禁

- 完整 `pytest`。
- `ruff check .`。
- `git diff --check`。
- 一次离线 Streamlit runner smoke，确认岗位、诊断和四类产物仍可生成。

## 兼容与发布

- 新字段放入 metadata/诊断结构，不改变已有 CLI 参数或 `JobPosting` 必填字段。
- 保留 `resolution_log.strategy` 与现有 `url_verification` 值，减少下游兼容风险。
- 默认启用永久失效门禁，因为继续展示明确 404/410 链接属于错误行为。
- 在线来源会随时间变化；真实网络 smoke 只能作为当次证据，不写入确定性测试断言。

## 验收标准

1. 官方来源异常不再静默消失，JSON 中能查到每个配置来源的最终状态。
2. 404/410 或明确下线页不能借助列表 JD 进入最终岗位结果。
3. 403、429、超时和 5xx 不被错误标记为岗位下线，并仍可诚实降级。
4. Streamlit 诊断页能区分来源故障与页面故障。
5. 现有页面核验标签语义保持不变。
6. 完整测试、Ruff、diff 检查和离线 smoke 全部通过。
