# 岗位地点严格过滤设计

> 日期：2026-09-18  
> 背景：实时岗位运行 `run-b9adb0a8` 的用户地点为“深圳”，但结果仍包含纯北京、上海和未知地点岗位。

## 问题定义

当前实时官方 API 模式仅把 `UserProfile.location` 保存在任务中：来源发现阶段只接收数量上限，匹配器只计算技能匹配。因此“地点”不是结果约束。

本轮只修复地点语义。岗位关键词的精确查询/排序需要单独设计，不与本次地点过滤捆绑。

`深圳` 只是 `run-b9adb0a8` 的当次输入和验收样例，不是固定规则或配置项。过滤目标必须在每次任务运行时动态读取当次 `UiRunRequest.location`，并通过 `UserProfile.location` 传入工作流。用户改成“北京”、“上海”或“远程”后，新任务的结果应立即改用新值过滤，不依赖进程启动时的值，也不复用上一次任务的地点。

## 方案对比

### A. 抽取后的统一硬过滤（采用）

在抽取器产出 `JobPosting`、校验器确认岗位有效后，但在技能匹配和持久化之前，根据用户地点过滤。

优点：一处实现覆盖官方 API、聚合文件、指定 URL 和 Demo；可以使用最终抽取地点；行为容易回归测试。

代价：会先访问部分不匹配的页面；过滤后的岗位数可能少于目标数，但不用错误城市凑数。

### B. 向每个来源下推地点参数

优点：减少无关页面访问，理论上更容易补足目标数。

缺点：42 个来源的 API 地点参数和编码不统一，部分来源不支持地点筛选；容易出现源间语义不一致。不作为本轮方案。

### C. 只降低异地岗位排名

优点：结果数量稳定，可保留跨城市机会。

缺点：与用户确认的“严格按当次输入地点过滤”冲突。不采用。

## 过滤语义

1. 用户地点为 `全国`、`不限`、`任意` 或对应英文通配词时，不启用地点过滤。
2. 用户地点为具体城市时，只保留地点包含当次输入城市的岗位。代码中不得出现硬编码的“深圳”特例。
3. 多城市岗位只要包含目标城市就保留。例如“深圳总部、北京、上海”匹配“深圳”。
4. 兼容行政区后缀和常见分隔符：“深圳”与“深圳市”等价，“广东省-深圳市”可匹配“深圳”。
5. `Remote` 与“远程”互为别名，但不是“全国”通配符。
6. 具体城市搜索下，空地点和 `Unknown Location` 均排除；不猜测企业所在地。
7. 过滤后结果可少于“目标岗位数”。该字段在本轮中解释为扫描/输出上限，不保证用其他城市补满。

## 组件与数据流

1. 新增一个无副作用的地点判定函数，输入为动态的 `requested_location` 和岗位 `actual_location`，输出为匹配布尔值。该函数不保存任何跨任务状态。
2. Streamlit 每次提交表单时都使用当前地点框构造新的 `UiRunRequest`；`run_ui_request` 将该值写入本次 `UserProfile.location`。
3. 工作流在 verifier 节点中先执行现有岗位质量校验，再用本次 `state.user.location` 对通过校验的岗位执行地点过滤。
4. 地点不匹配的岗位不进入 `state.jobs`、技能匹配、数据库、报告和界面结果。
5. 被排除岗位写入现有 `metadata.filtered_jobs`，原因为可读的 `location mismatch` 或 `location unknown`，诊断同时包含当次动态请求地点和岗位实际地点。
6. `metrics.valid_jobs` 统计地点过滤后的最终结果数。

## 错误与边界处理

- 地点字符串异常不中断任务；具体城市搜索时按不匹配处理并记录诊断。
- 不将“公司总部”、岗位标题或其他非地点字段用作猜测证据。
- 本轮不做地理距离、通勤圈或“深圳周边”扩展。

## 测试设计

### 纯函数测试

- `深圳` 匹配 `深圳`、`深圳市`、`广东省-深圳市` 和 `深圳总部、北京、上海`。
- `深圳` 不匹配 `北京市`、`上海` 或 `Unknown Location`。
- `全国` 保留任意地点，包括未知地点。
- `Remote` 与“远程”相互匹配。

### 工作流回归测试

- 用户搜索“深圳”时，混合候选中只保留深圳和包含深圳的多城市岗位。
- 使用同一个工作流实例连续运行“深圳”和“北京”两个任务时，第二次必须按北京过滤，不受第一次深圳输入影响。
- 参数化覆盖“深圳”、“北京”、“上海”和“远程”，证明实现没有硬编码特定城市。
- 纯北京/上海与未知地点出现在 `filtered_jobs`，并带有明确原因。
- 经过滤的岗位不进入匹配、持久化和报告，`valid_jobs` 与最终岗位数一致。
- 用户搜索“全国”时保留现有行为。

## 验收标准

- 使用“深圳”重跑截图对应场景时，结果中不再出现纯北京、上海或未知地点岗位。
- 腾讯多城市岗位和小米深圳岗位可保留。
- 把表单地点改为“北京”并新运行后，结果改为只保留包含北京的岗位；改为“全国”后恢复不限地点。
- “失败与诊断”可解释被排除岗位的目标地点和实际地点。
- 新增测试必须在生产代码修改前因当前缺少地点过滤而失败，修复后通过。
- 完整测试、Ruff 和 `git diff --check` 通过。

## 不在本轮范围

- 不逐个改造 42 个来源适配器的查询参数。
- 不保证严格过滤后仍填满目标岗位数。
- 不在本轮重新定义岗位关键词的搜索/排序语义。
- 不引入地图、地理编码或外部城市数据库。
